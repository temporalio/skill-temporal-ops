# Temporal Cloud -- mTLS Certificate Management

Quick-reference for generating, uploading, filtering, and rotating mTLS certificates on Temporal Cloud using `tcld`.

> For diagnosing certificate errors (x509 failures, TLS handshake errors), see the triage file `../triage/certificates.md`.

---

## Namespace ID format

All `--namespace` flags accept a **Namespace ID** in the format `<namespace_name>.<account_suffix>` (e.g., `your-namespace.a1b2c`). <!-- docs/cloud/tcld/namespace.mdx:27 -->

If `--namespace` is omitted, the value of the environment variable `$TEMPORAL_CLOUD_NAMESPACE` is used. <!-- docs/cloud/tcld/namespace.mdx:63 -->

## 1. Generating certificates with tcld

### 1a. Generate a CA certificate

```bash
tcld generate-certificates certificate-authority-certificate \
    --organization <value> \
    --validity-period <duration> \
    --ca-certificate-file <path>.pem \
    --ca-key-file <path>.key
```
<!-- docs/cloud/tcld/generate-certificates.mdx:24-81 -->

Alias for the subcommand: `ca` <!-- docs/cloud/tcld/generate-certificates.mdx:30 -->

| Flag | Alias | Purpose |
|---|---|---|
| `--organization` | `--org` | Organization name for the certificate <!-- docs/cloud/tcld/generate-certificates.mdx:36 --> |
| `--validity-period` | `-d` | Duration in `d/h` format (e.g. `30d10h`) <!-- docs/cloud/tcld/generate-certificates.mdx:48 --> |
| `--ca-certificate-file` | `--ca-cert` | Output path for the `.pem` CA certificate <!-- docs/cloud/tcld/generate-certificates.mdx:59 --> |
| `--ca-key-file` | `--ca-key` | Output path for the `.key` private key <!-- docs/cloud/tcld/generate-certificates.mdx:71 --> |
| `--rsa-algorithm` | `--rsa` | Use 4096-bit RSA instead of ECDSA P-384 (disabled by default) <!-- docs/cloud/tcld/generate-certificates.mdx:83 --> |

Default key algorithm: ECDSA P-384. <!-- docs/cloud/tcld/generate-certificates.mdx:85 -->

A CA certificate generated by tcld has a maximum duration of 1 year (`-d 1y`) and a minimum duration of 7 days. <!-- docs/cloud/get-started/certificates.mdx:129-130 -->

**Shorthand example** (from docs):

```bash
tcld gen ca --org temporal -d 1y --ca-cert ca.pem --ca-key ca.key
```
<!-- docs/cloud/get-started/certificates.mdx:138 -->

### 1b. Generate an end-entity (leaf) certificate

```bash
tcld generate-certificates end-entity-certificate \
    --organization <value> \
    --validity-period <duration> \
    --ca-certificate-file <ca>.pem \
    --ca-key-file <ca>.key \
    --certificate-file <leaf>.pem \
    --key-file <leaf>.key
```
<!-- docs/cloud/tcld/generate-certificates.mdx:96-187 -->

| `--organization-unit` | _(none)_ | Optional OU name <!-- docs/cloud/tcld/generate-certificates.mdx:119 --> |
| `--common-name` | _(none)_ | Optional common name <!-- docs/cloud/tcld/generate-certificates.mdx:77 --> |
| `--validity-period` | `-d` | Duration in `d/h` format <!-- docs/cloud/tcld/generate-certificates.mdx:131 --> |
| `--ca-certificate-file` | `--ca-cert` | Path to the signing CA `.pem` <!-- docs/cloud/tcld/generate-certificates.mdx:143 --> |
| `--ca-key-file` | `--ca-key` | Path to the signing CA `.key` <!-- docs/cloud/tcld/generate-certificates.mdx:155 --> |

## 2. CA certificate requirements

CA certificates uploaded to Temporal Cloud must meet all of the following: <!-- docs/cloud/get-started/certificates.mdx:48-83 -->

- X.509v3
- Each certificate must be a root certificate or issued by another certificate in the bundle
- Must include `CA: true`
- Cannot be a well-known CA (e.g. DigiCert, Let's Encrypt) unless certificate filters are also specified
- Signing algorithm: RSA or ECDSA with SHA-256 or stronger (SHA-1 and MD5 rejected)
- Cannot be generated with a passphrase
- Bundle limit: up to 16 CA certificates, max 32 KB payload before base64 encoding <!-- docs/cloud/get-started/certificates.mdx:80-83 -->

End-entity certificates must include `CA: false` and Digital Signature key usage. <!-- docs/cloud/get-started/certificates.mdx:92-96 -->

Each certificate in the chain (from end-entity to root) must have a unique Distinguished Name. Distinguished Names are not case sensitive. <!-- docs/cloud/get-started/certificates.mdx:53-59 -->

## 3. Uploading CA certificates to a Namespace

### 3a. Add a CA certificate (appends to existing)

```bash
tcld namespace accepted-client-ca add \
    --namespace <namespace_name>.<account_suffix> \
    --ca-certificate-file <path>
```
<!-- docs/cloud/tcld/namespace.mdx:780-865 -->

Alias: `a` <!-- docs/cloud/tcld/namespace.mdx:784 -->

| Flag | Alias | Notes |
|---|---|---|
| `--ca-certificate` | `-c` | Base64-encoded CA certificate PEM string <!-- docs/cloud/tcld/namespace.mdx:837 --> |
| `--ca-certificate-file` | `-f` | Path to CA certificate PEM file <!-- docs/cloud/tcld/namespace.mdx:853 --> |
| `--namespace` | `-n` | Namespace ID <!-- docs/cloud/tcld/namespace.mdx:789 --> |
| `--resource-version` | `-v` | ETag; uses latest if omitted <!-- docs/cloud/tcld/namespace.mdx:819 --> |
| `--request-id` | `-r` | Request identifier for async op <!-- docs/cloud/tcld/namespace.mdx:805 --> |

If both `--ca-certificate` and `--ca-certificate-file` are specified, only `--ca-certificate` is used. <!-- docs/cloud/tcld/namespace.mdx:839-840 -->

### 3b. Set CA certificates (replaces all existing)

```bash

    --namespace <namespace_name>.<account_suffix> \

```

Alias: `s` <!-- docs/cloud/tcld/namespace.mdx:1009 -->

Same flags as `add` (`--ca-certificate` / `--ca-certificate-file`, `--namespace`, `--resource-version`, `--request-id`).

### 3c. List current CA certificates

```bash
    --namespace <namespace_name>.<account_suffix>
```


## 4. Certificate filters

Certificate filters restrict which end-entity certificates can connect, based on DN fields. <!-- docs/cloud/tcld/namespace.mdx:1121-1125 -->

A filter can include any combination (at least one) of: <!-- docs/cloud/tcld/namespace.mdx:1348-1353 -->

- `commonName`
- `organization`
- `organizationalUnit`
- `subjectAlternativeName`

Maximum 25 certificate filters per Namespace. <!-- docs/cloud/get-started/certificates.mdx:421 -->

Matching is case-insensitive. A single `*` wildcard is allowed at the beginning or end (but not both) of a value. A bare `*` is not valid. <!-- docs/cloud/get-started/certificates.mdx:416-419 -->

If a well-known CA certificate is configured, you cannot clear certificate filters. <!-- docs/cloud/get-started/certificates.mdx:423-424 -->

JSON format for filter definitions: <!-- docs/cloud/tcld/namespace.mdx:1362 -->

```json
{ "filters": [ { "commonName": "test1" } ] }
```

### 4a. Import (set) certificate filters

Replaces any existing filters with the ones provided.

```bash
tcld namespace certificate-filters import \
    --namespace <namespace_name>.<account_suffix> \
    --certificate-filter-file <path>
```
<!-- docs/cloud/tcld/namespace.mdx:1339-1435 -->

Alias: `imp` <!-- docs/cloud/tcld/namespace.mdx:1344 -->

| Flag | Alias | Notes |
|---|---|---|
| `--certificate-filter-file` | `--file`, `-f` | Path to JSON file <!-- docs/cloud/tcld/namespace.mdx:1359 --> |
| `--certificate-filter-input` | `--input`, `-i` | Inline JSON string <!-- docs/cloud/tcld/namespace.mdx:1375 --> |

If both `--certificate-filter-file` and `--certificate-filter-input` are specified, the command returns an error. <!-- docs/cloud/tcld/namespace.mdx:1364-1365 -->

### 4b. Add certificate filters (appends)

## 5. Certificate rotation procedure (zero-downtime)

This is the rollover process documented for both UI and tcld. <!-- docs/cloud/get-started/certificates.mdx:340-400 -->

### Using tcld

1. Create a single PEM file containing both old and new CA certificates concatenated: <!-- docs/cloud/get-started/certificates.mdx:378-388 -->

   ```
   -----BEGIN CERTIFICATE-----
   ... old CA cert ...
   -----END CERTIFICATE-----
   -----BEGIN CERTIFICATE-----
   ... new CA cert ...
   -----END CERTIFICATE-----
   ```

2. Upload the bundle: <!-- docs/cloud/get-started/certificates.mdx:390-393 -->

   ```bash
   tcld namespace accepted-client-ca set --ca-certificate-file <path>
   ```

3. Monitor traffic to the old certificate until it ceases. <!-- docs/cloud/get-started/certificates.mdx:395 -->

4. Create a file containing only the new CA certificate. <!-- docs/cloud/get-started/certificates.mdx:397 -->

5. Run `set` again with the new-only file to remove the old CA: <!-- docs/cloud/get-started/certificates.mdx:399 -->

   ```bash
   tcld namespace accepted-client-ca set --ca-certificate-file <path>
   ```

### Using the Cloud UI

1. Navigate to **Namespaces** > select Namespace > **Edit** > **Authentication**. <!-- docs/cloud/get-started/certificates.mdx:351 -->
2. Scroll past the existing certificate's `-----END CERTIFICATE-----` and paste the new PEM block on the next line. <!-- docs/cloud/get-started/certificates.mdx:359-360 -->
3. **Save**. <!-- docs/cloud/get-started/certificates.mdx:363 -->
4. Wait until all Workers are using the new certificate. <!-- docs/cloud/get-started/certificates.mdx:365 -->
5. Return to **Edit** > **Authentication**, delete the old certificate, and **Save**. <!-- docs/cloud/get-started/certificates.mdx:367-371 -->

## 6. Namespace auth method: mTLS vs API keys

When creating a Namespace, `--auth-method` selects the authentication mode. <!-- docs/cloud/tcld/namespace.mdx:122 -->

Valid values: `mtls`, `api_key`, `restricted`, `api_key_or_mtls` <!-- docs/cloud/tcld/namespace.mdx:489 -->

- `mtls` (default): requires `--ca-certificate` or `--ca-certificate-file` <!-- docs/cloud/tcld/namespace.mdx:124 -->
- `api_key`: no certificate flags needed <!-- docs/cloud/tcld/namespace.mdx:125 -->
- `api_key_or_mtls`: accepts both authentication methods simultaneously (requires flexible auth to be enabled; contact [Temporal Support](https://docs.temporal.io/cloud/support#ticketing) to enable it)

```bash
tcld namespace create \
    --namespace <namespace_name>.<account_suffix> \
    --region us-east-1 \
    --auth-method api_key
```
<!-- docs/cloud/tcld/namespace.mdx:130-134 -->

Creating with mTLS:

```bash
tcld namespace create \
    --namespace <namespace_name>.<account_suffix> \
    --region us-east-1 \
    --ca-certificate-file ca.pem
```
<!-- docs/cloud/tcld/namespace.mdx:124 (--auth-method defaults to mtls) -->

Certificate filters can optionally be set at create time via `--certificate-filter-file` or `--certificate-filter-input`. <!-- docs/cloud/tcld/namespace.mdx:149-164 -->

## 7. Handling a compromised end-entity certificate

Temporal does not support or check certificate revocation lists (CRLs). <!-- docs/cloud/get-started/certificates.mdx:269-270 -->

Recommended approach: use short-lived end-entity certificates so a compromised one expires quickly. <!-- docs/cloud/get-started/certificates.mdx:273-275 -->

If immediate action is needed: <!-- docs/cloud/get-started/certificates.mdx:278-320 -->

1. If using certificate filters, set filters to block the compromised certificate.
2. Otherwise, generate a new CA certificate.
3. Deploy the new CA alongside the existing one (so existing end-entity certs continue working).
4. Regenerate all end-entity certificates from the new CA.
5. Remove the old (compromised) CA certificate from the Namespace.
6. Monitor audit logs for unauthorized access.

## 9. Expiration notifications

Temporal Cloud sends email notifications 15 days before certificate expiration. <!-- docs/cloud/get-started/certificates.mdx:337 -->

An expired root CA invalidates all downstream certificates. An expired end-entity certificate prevents Temporal Clients from connecting or starting Workflow Executions. Workers with expired certs will either stall indefinitely or cause Workflow timeouts. <!-- docs/cloud/get-started/certificates.mdx:30-38 -->
